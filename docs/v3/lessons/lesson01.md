# 第 01 课：并发的代价、竞态与证据

> 参考骨架：《Java并发编程的艺术》第 1 章“并发编程的挑战”
>
> 技术基线：Java 21、Maven、JUnit 5
>
> 建议用时：2.5 小时
> 本课原则：先证明问题存在，不提前用锁或原子类掩盖问题。

## 一、本课完成后，你真正获得什么

本课不是让你记住几个并发名词，而是建立以后七课都会重复使用的诊断顺序：

```text
找到共享状态
→ 写出最小状态转换
→ 构造关键线程交错
→ 观察错误结果或活跃性故障
→ 给出可重复证据
→ 再选择正确性策略
```

完成本课后，你应该能够：

1. 判断一段代码里哪些状态可能被多个线程访问，而不是看到局部变量就误判为
   “线程安全”。
2. 把 `counter++` 拆成读取、计算、写回，准确解释丢失更新发生在哪一步。
3. 区分安全性、活跃性和性能问题，并说明多线程为什么不一定更快。
4. 识别死锁的四个必要条件，使用线程转储建立证据，而不是靠猜。
5. 说明“运行成功一次”和“并发正确”之间为什么没有必然关系。
6. 使用统一结构回答本课对应的 Q02、Q04、Q05、Q22、Q52、Q68。

## 四、核心原理一：共享状态与丢失更新

### 4.1 并发和并行不是同一个问题

- **并发**描述多个任务的生命周期发生重叠，它们可能在单核上交替推进。
- **并行**描述多个计算在同一时刻实际执行，通常需要多个执行资源。
- 并发可以改善响应性或吞吐，也可能只是引入调度和协作成本。

是否值得并发，至少要同时检查：任务能否拆分、串行比例、工作粒度、共享程度、
真实瓶颈以及下游容量。线程数量增加并不会自动增加数据库连接、磁盘带宽或远端
服务配额。

### 4.2 哪些状态算共享

只要同一个可变对象可以被多个线程触达，它就可能构成共享状态。常见入口包括：

| 代码形态 | 是否天然线程安全 | 判断依据 |
|---|---|---|
| 方法内新建且从不逸出的可变对象 | 通常是 | 对象只被当前线程触达，属于线程封闭 |
| 方法内的局部引用指向公共对象 | 否 | 引用是局部的，引用指向的对象仍然共享 |
| 实例字段所在对象被多个线程持有 | 否 | 同一字段可被并发读写 |
| 可变静态字段 | 否 | 类加载器范围内通常可被多线程触达 |
| 正确构造并安全发布的不可变对象 | 通常是 | 共享读取不改变状态，但仍要证明安全发布 |
| 普通集合被包装为不可修改视图 | 不一定 | 视图不可改不等于底层集合不会被别处修改 |

判断时不要只看变量声明在哪里，还要沿着引用关系追踪对象是否逃逸给其他线程。

### 4.3 堆共享字段与线程栈快照

设堆中只有一个共享对象 `statistics`，其字段 `completed = 0`。两个线程都执行
逻辑上的读取、加一、写回：

```text
                         堆：同一个共享对象
                    ┌──────────────────────┐
                    │ statistics.completed │
                    │          0           │
                    └──────────┬───────────┘
                               │ 两个线程都可访问
              ┌────────────────┴────────────────┐
              │                                 │
线程 A 的执行帧/私有快照                  线程 B 的执行帧/私有快照
┌──────────────────────┐                ┌──────────────────────┐
│ observed = 尚未读取   │                │ observed = 尚未读取   │
│ next     = 尚未计算   │                │ next     = 尚未计算   │
└──────────────────────┘                └──────────────────────┘
```

一种发生丢失更新的交错是：

| 步骤 | 线程 A 私有快照 | 堆字段 | 线程 B 私有快照 | 真正发生的动作 |
|---:|---:|---:|---:|---|
| 0 | — | 0 | — | 初始状态 |
| 1 | `observed=0` | 0 | — | A 读取共享字段 |
| 2 | `observed=0` | 0 | `observed=0` | B 读取同一个共享字段 |
| 3 | `next=1` | 0 | `observed=0` | A 在自己的执行上下文计算 |
| 4 | `next=1` | 0 | `next=1` | B 在自己的执行上下文计算 |
| 5 | `next=1` | 1 | `next=1` | A 写回共享字段 |
| 6 | `next=1` | 1 | `next=1` | B 也写回 1；A 的更新被覆盖 |

两次业务操作完成，堆字段却只增加一次。这就是 read-modify-write 被线程交错后
出现的**丢失更新**。

这里的“线程栈/私有快照”是帮助推理的语义图，不是对 HotSpot 物理实现的承诺。
JIT 可能把中间值放在寄存器中，也可能消除或改写某些操作；Java 规范并不要求
每个局部值都实际写入一块可见的栈内存。同理，本课不会用“每个线程把变量从主
内存复制到工作内存”代替 JMM 规则。第 03 课会正式用 happens-before 描述可见性。

### 4.4 竞态条件与数据竞争

这两个词经常混用，但面试中最好分层表达：

- **竞态条件**：程序的业务正确性依赖不可控的执行先后。例如“检查库存后扣减”
  的检查与更新被其他线程插入。
- **数据竞争**：两个线程访问同一变量，至少一个是写，并且缺少可以排序这些访问
  的同步关系。

`completed++` 在共享普通字段上执行时，两者通常同时存在。竞态描述业务结果对
时序的依赖；数据竞争强调内存访问缺少同步约束。

### 4.5 Q68：两个线程各自加 50 次，应怎样回答

不要从一个数字范围开始背。先声明假设，再建立模型：

1. 两个线程是否都确实启动并正常完成？
2. 最终读取前是否 `join` 两个线程？
3. 被更新的是普通 `int`、`volatile int`，还是原子类型？
4. “加一”是否就是普通的 read-modify-write，期间有没有其他同步？
5. 问的是某次常见运行结果，还是 Java 规范保证？

对于共享普通 `int` 的 `++`，单次读取和写入不能把整个复合操作变为原子操作，
因此不能保证最终结果是 100。`join` 让最终观察者在两个线程结束后读取结果，但
不会修复两个工作线程之间已经发生的丢失更新。把字段改成 `volatile` 也不能把
`++` 合成一个不可分割动作。

常见的“结果一定在某个固定范围”通常隐含了简化交错模型，不能不加前提地当作
Java 规范结论。本课验收关注的是：你能否构造一条合法的丢失更新交错，并说明
为何“必须等于 100”的断言不成立。

## 五、核心原理二：并发代价与死锁

### 5.1 多线程的成本清单

| 成本 | 表现 | 本课怎样建立证据 |
|---|---|---|
| 任务拆分与合并 | 需要切分输入、汇总结果、传播失败 | 比较串行基线与并发流程的额外步骤 |
| 调度与上下文切换 | 可运行线程过多时，CPU 时间消耗在切换和调度 | 只作现象观察；严谨性能结论留给 JFR/JMH |
| 同步与竞争 | 锁等待、CAS 重试、缓存一致性通信都会消耗资源 | 先定位共享写热点，不用单次耗时下结论 |
| 内存与生命周期 | 每个任务、线程、队列元素和上下文都占用资源 | 记录任务数、线程数、队列/对象数量 |
| 外部资源限制 | 数据库连接、文件句柄、远端配额不会随线程增加 | 明确真实容量，拒绝“线程越多吞吐越高” |
| 排障复杂度 | 故障依赖时序，日志可能改变时序 | 使用确定性交错、超时和线程转储 |

单次 `System.nanoTime()` 或肉眼看到“并发版更快”都不是可靠基准。性能问题需要
预热、隔离变量和统计分布，第 08 课再使用 JMH/JFR 完成严谨测量。本课只建立
“先测量、再下结论”的习惯。

### 5.2 安全性、活跃性、性能必须分开

- **安全性**：不发生错误的状态，例如计数不丢失、对象不暴露半初始化状态。
- **活跃性**：系统还能继续推进，例如不死锁、不永久等待、不饥饿。
- **性能**：在正确且能推进的前提下，延迟、吞吐和资源消耗是否达标。

一个程序可能数据完全正确却永久卡住，也可能跑得很快却持续丢数据。评审并发代码
时，三个维度必须分别给证据。

### 5.3 死锁的四个必要条件

死锁通常需要四个条件同时成立：

| 必要条件 | 含义 | 常见破坏方式 |
|---|---|---|
| 互斥 | 资源同一时刻只能被一个参与者持有 | 减少独占资源；可行时改为不可变或无共享 |
| 持有并等待 | 持有一个资源时继续等待另一个 | 一次申请所需资源，或获取失败后释放已持有资源 |
| 不可抢占 | 资源不能被外部强行安全夺走 | 使用可取消/超时协议，让持有者主动退出并释放 |
| 循环等待 | A 等 B 持有的资源，B 又直接或间接等 A | 建立全局锁顺序，所有路径按同一顺序获取 |

典型关系图：

```text
线程 A ──持有──> 锁 X ──被等待──> 线程 B
线程 A <──被等待── 锁 Y <──持有── 线程 B

等价等待环：线程 A → 锁 Y → 线程 B → 锁 X → 线程 A
```

“多加一把锁”通常不能解决死锁，甚至可能增加等待环。常用策略是：缩小锁作用域、
固定锁顺序、避免持锁调用未知外部代码、使用有界等待并在失败时完整回滚。超时并
不自动保证业务正确，它只是把无限等待变成调用方可以处理的失败路径。

### 5.4 死锁证据应包含什么

至少需要以下三层证据：

1. **状态证据**：测试在明确超时内无法完成，而不是无限等待测试进程。
2. **资源关系证据**：线程转储显示每个线程持有的监视器和正在等待的监视器。
3. **代码路径证据**：两条调用路径的锁获取顺序确实构成环。

只看到两个线程处于 `BLOCKED` 还不够；短暂竞争也会阻塞。只有等待关系形成闭环，
并与代码锁顺序对应，才能诊断为死锁。

## 六、核心原理三：一致性和线程安全策略

### 6.1 Q05：先确定一致性的作用域

“保证数据一致性有哪些方案”没有脱离场景的万能答案。先问数据在哪一层：

| 作用域 | 常见策略 | 不能替代什么 |
|---|---|---|
| 单线程内部 | 局部变量、顺序执行、不变式 | 不能约束其他线程访问共享对象 |
| 单 JVM 多线程 | 线程封闭、不可变对象、锁、原子操作、并发容器 | 不能自动协调其他进程或数据库事务 |
| 多进程/多实例 | 外部协调、版本号、幂等、分布式互斥或消息协议 | 需要处理租约、故障和网络分区 |
| 数据库 | 事务隔离、约束、乐观版本、行锁 | JVM 锁不能保护另一个应用实例 |
| 跨系统流程 | 幂等键、Outbox、补偿、状态机 | 本地 ACID 不能覆盖全部远端系统 |

本课的代码只处理单 JVM 内的共享状态，但面试时必须先说明边界，避免回答成锁
类名清单。

### 6.2 Q22：线程安全的选型顺序

优先级不是“先上最强的锁”，而是逐层减少共享和协议复杂度：

```text
能不共享吗？
├─ 能：线程封闭、按任务创建状态
└─ 不能：状态能不可变吗？
   ├─ 能：不可变值 + 安全发布
   └─ 不能：更新是否只有一个独立变量？
      ├─ 是：考虑原子更新（第 04 课）
      └─ 否：是否存在跨字段不变式或条件等待？
         ├─ 是：使用同一互斥协议/Lock/Condition（第 04～05 课）
         └─ 否：数据流能否交给成熟并发组件？
            └─ 队列、并发容器、同步工具或 Executor（第 06～07 课）
```

选型后还必须回答：所有访问是否都遵守同一协议、失败和取消时是否释放资源、协议
是否覆盖完整不变式、测试如何证明关键交错。只把某个方法标成 `synchronized`
并不自动保护对象的所有使用方式。

### 6.3 本课 TASK 的边界

TaskHub 第 01 课只建立：

- 一个明确的任务完成统计契约；
- 普通 `int completedTasks` 字段的串行读写基线；
- `CompletionUpdateProbe` 提供的“读完后”观测点；
- 一条能被验收测试安排出丢失更新的不安全 read-modify-write 路径。

你需要根据 `TASK` 文件中的注释和测试完成 TODO。步骤契约以 TASK 注释为准，
但讲义和学习分支不提供完整参考实现。以下做法会让本课失去训练价值：

- 修改或删除验收断言；
- 返回写死的统计结果；
- 使用 `sleep` 猜测线程先后；
- 为了让测试变绿，直接换成原子类、`synchronized` 或 `Lock`；
- 删除不安全反例，只留下“正确版”；
- 启动无法在超时后回收的非守护线程。

## 七、什么才算并发证据

### 7.1 证据强度

| 做法 | 能说明什么 | 不能说明什么 |
|---|---|---|
| 运行一次结果正确 | 该次被观察到的执行没有失败 | 其他交错也正确 |
| 循环运行后偶尔失败 | 至少存在错误执行 | 尚未命中的路径是否正确 |
| 使用 `sleep` 扩大窗口 | 可能提高某种交错概率 | 不能保证目标交错发生，机器变化会失效 |
| 使用屏障/闩锁/测试钩子控制步骤 | 可以稳定构造指定交错 | 不能穷尽所有可能交错 |
| 超时 + 线程转储 | 可以证明未推进及等待关系 | 仍需结合代码确认根因 |
| 同步规则/HB 推理 + 针对性测试 | 可以同时解释协议和实测行为 | 仍要保持实现与证明假设一致 |

### 7.2 本课验收的最低标准

1. **确定性功能测试**：串行基线的期望值与实际值一致。
2. **并发时序测试**：不依赖概率，能构造并观察一次指定的丢失更新。
3. **活跃性故障证据**：`DeadlockDemoTest` 在测试超时保护内检出真实等待环；
   TASK 中的 `@Timeout` 是防挂保护，不代表另外一个业务失败契约。
4. **解释性证据**：你能把测试中的每个关键步骤映射到堆字段或线程私有快照。
5. **边界声明**：你不把一个测试通过说成对所有线程交错的数学证明。

以后课程会继续增加 jcstress、JMH、JFR 和生产诊断证据。本课先把“可重复”和
“能解释”做好。

## 八、六道面试题的本课回答骨架

先独立口述，再查看下面的检查点。不要把检查点背成固定话术。

### Q02：Java 多线程是什么，需要注意什么？

- 结论中区分并发与并行，并说明线程共享进程内对象的能力和风险。
- 原理包含共享状态、调度交错和内存可见性，而不是只说“提高效率”。
- 边界覆盖安全性、活跃性、性能、资源容量和可诊断性。
- 证据引用本课丢失更新或死锁实验。

### Q04：使用多线程要注意哪些问题？

- 按正确性、活跃性、性能和工程治理分类，不堆砌 API 名称。
- 提到异常传播、取消/超时、资源释放、线程数量、上下文传递和测试困难。
- 给出一个“多线程反而更慢或更危险”的具体条件。

### Q05：保证数据一致性有哪些方案？

- 第一问必须是“一致性发生在哪个边界”。
- 单 JVM 内优先避免共享/不可变，再考虑同步协议和成熟并发组件。
- 跨进程与数据库需要版本、事务、幂等或外部协调，JVM 锁不能越界生效。

### Q22：怎么保证多线程安全？

- 先定义需要维持的不变式和共享状态。
- 使用本讲义的选型顺序，并说明所有访问必须服从同一协议。
- 用测试复现关键交错，再用同步关系解释为什么修复成立。

### Q52：什么情况会产生死锁，如何解决？

- 完整说出四个必要条件。
- 至少给出锁顺序与有界获取两种不同方向的策略。
- 说明如何通过超时、线程转储和源码锁顺序形成证据链。

### Q68：两个线程各自对同一整数加 50 次，结果可能是什么？

- 先补齐线程完成、最终读取方式、字段类型和同步方式等假设。
- 拆解 read-modify-write，并画出至少一条丢失更新交错。
- 核心结论是不保证 100；不要把特定 JVM 的一次观察或简化模型范围冒充规范保证。
- 说明 `join`、`volatile` 各自能解决什么、不能解决什么。

## 九、常见误区检查表

| 误区 | 正确校正 |
|---|---|
| “局部变量一定线程安全” | 局部引用可能指向共享可变对象，必须检查对象是否逃逸 |
| “`int` 读写是原子的，所以 `i++` 是原子的” | `++` 是复合状态转换，组成步骤可被其他线程穿插 |
| “`volatile` 能让所有更新线程安全” | 它不把 read-modify-write 自动变成不可分割操作 |
| “`join` 能修复工作线程间的竞态” | `join` 约束结束后的观察，不回滚已经丢失的更新 |
| “测试跑一万次没失败就是正确” | 未观察到失败不是同步协议证明 |
| “加 `sleep` 就能稳定复现” | `sleep` 只影响概率，不提供目标时序保证 |
| “出现 `BLOCKED` 就是死锁” | 正常锁竞争也会阻塞，死锁需要闭环等待证据 |
| “多线程一定比单线程快” | 拆分、调度、同步、内存和下游容量都可能抵消收益 |
| “加锁越多越安全” | 锁协议不完整仍会错，嵌套锁还会增加死锁风险 |
| “JVM 锁能保证数据库多实例一致性” | 进程内同步无法覆盖其他进程和外部系统 |

## 十、权威校验点

本课的代码与结论可以回到以下 Java 21 一手资料核对：

- [JLS 17.4.5：Happens-before Order](https://docs.oracle.com/javase/specs/jls/se21/html/jls-17.html#jls-17.4.5)：
  定义数据竞争，并给出 `Thread.start()` 和成功 `join()` 建立的 happens-before 边；
- [Java SE 21 ThreadMXBean API](https://docs.oracle.com/en/java/javase/21/docs/api/java.management/java/lang/management/ThreadMXBean.html)：
  `findDeadlockedThreads()` 可以查找等待监视器或 ownable synchronizer 的平台线程死锁环；
- [JDK 21 jcmd 命令](https://docs.oracle.com/en/java/javase/21/docs/specs/man/jcmd.html)：
  `Thread.print -l` 输出线程栈和 `java.util.concurrent` 锁信息。

`ThreadMXBean` 的这些线程列表与死锁检测 API 面向平台线程，不要推广为所有
虚拟线程的通用诊断契约。第 08 课会专门处理虚拟线程诊断。
