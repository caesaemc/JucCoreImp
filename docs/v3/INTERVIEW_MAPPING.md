## 使用规则

这份矩阵只保留题目主题和原创考察点，不复制来源页面的答案。

每道题在 V3 中只分配给一个主课次，避免多课重复讲解。相近题仍保留各自的
来源编号，但会合并为一次训练，并从不同追问角度验收。

V3 的回答标准统一为：

```text
结论
→ Java 规范或 API 语义
→ 运行机制
→ 适用边界
→ 本课代码与测试证据
```

标记说明：

- `核心`：本课必须独立回答。
- `合并`：与另一题共用一条知识主线，但追问角度不同。
- `校正`：来源答案或常见说法需要按 Java 21、规范语义重新核对。
- `场景`：必须用代码、时序图或测试回答。

## 需要优先校正的说法

V3 不直接继承来源答案，以下题目必须先查规范、Java 21 API 或当前实现：

- Q09：`interrupt()` 本身不保证立即抛出异常。
- Q12：`sleep()`、CPU 调度与释放监视器是三个不同问题。
- Q16：`notify()` 不提供 FIFO 选择保证。
- Q33、Q34：偏向锁和锁升级口诀具有明显 JDK 版本背景。
- Q38：ThreadLocal 陈旧条目与泄漏风险需要结合线程生命周期说明。
- Q44：JMM 语义不能只用“刷主内存、缓存失效”解释。
- Q03、Q20：平台线程与操作系统线程的映射、虚拟线程调度器和载体线程实现
  不能写成 Java 语言保证；I/O 也不能绝对描述为“永远不会固定载体线程”。
- Q06、Q53、Q59、Q61：Runnable、Callable 和 Executor 描述任务或执行
  方式，不都属于“创建线程”；Java 21 还必须纳入虚拟线程 API，并说明虚拟
  线程不应被池化复用，也不会消除真实下游的容量边界。
- Q10、Q13、Q14：`Thread.State` 是 JVM 暴露的状态；`RUNNABLE` 不等于
  始终占用 CPU，被通知的线程还要重新竞争监视器。
- Q11、Q14～Q18、Q65：等待协议必须使用条件谓词循环，并覆盖虚假唤醒、
  丢失通知和中断；`wait()` 只释放调用对象的监视器。
- Q27、Q30：同步方法和同步代码块的字节码形式不同；普通 `lock()` 也不响应
  中断，只有 `lockInterruptibly()` 提供可中断获取。
- Q35～Q37：AQS 使用 CAS 更新状态是常见获取路径，但不能推导为所有状态
  变更都必须 CAS；语言/API 契约与当前 JDK 源码实现必须分层。
- Q48～Q51：`ReentrantLock` 默认也是非公平锁；公平构造参数不提供操作系统
  调度意义的绝对公平，无参 `tryLock()` 仍可插队。
- Q53～Q58：接纳流程判断 worker 数量而不是“线程是否忙”；关闭状态也会
  触发拒绝，核心线程可以超时，参数不能只套用 CPU 核数公式。
- Q63、Q64：关闭、`interrupt()` 与 `Future.cancel(true)` 都是协作式协议，
  不保证任务已经结束或立刻从队列物理移除。
- Q68：讨论结果范围前必须明确两个线程均完成、最终读取经过 `join`，以及
  采用何种读改写模型；核心结论是数据竞争不能保证得到 100。
